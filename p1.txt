# Phase 3 — Agent Runtime, Capability Management and Memory

## 1. Objective

Extend the existing web-based LLM Chatbox into a capable, extensible Agent system.

The application already has a Python backend, an HTML/JavaScript frontend, persistent conversations, Runs, Dialogue Workspaces, file versioning, and autosave.

Build on the existing implementation. Preserve its functionality and user experience.

The goal of Phase 3 is to let an Agent perform multi-step tasks using Skills and Tools, manage its working context efficiently, and propose improvements to its own capabilities under explicit user control.

The system must remain easy to understand, operate, inspect, and maintain.

**Use your engineering judgment to design the implementation.** The requirements below describe the intended behaviour and safety boundaries. They do not prescribe a specific class hierarchy, API structure, storage layout, or execution framework.

Prefer simple solutions that fit the existing codebase.

### Main deliverables

1. A persistent, single-Agent execution loop.
2. A Tool Registry and Skill Registry.
3. A web-based management interface for Skills, Tools, permissions, and approvals.
4. Frontend management of authorized external folders.
5. Version tracking for files written to external folders.
6. Controlled creation and upgrading of reusable Skills and Tools.
7. Capability version history, rollback, probation, promotion, and permanent deletion.
8. A restricted last-resort Python execution Skill.
9. Context-aware LLM execution planning and scheduling.
10. Conclusion-oriented Agent Memory with summarization and historical recall.
11. File-reference-based conversation context management.

Do not introduce unnecessary infrastructure, a database, Docker, WSL, or a multi-agent orchestration framework.

Retain native Windows support.

Do not implement Java Simulator integration or domain-specific research workflows in this phase.

---

## 2. Initial Investigation

Before writing code, inspect the existing application.

Understand how it currently manages:

- Model configuration and LLM requests.
- Streaming and reasoning output.
- Conversation state, Undo/Redo, and regeneration.
- Persistent Runs and reconnect behaviour.
- Dialogue Workspaces.
- Uploaded files.
- Generated files and Artifact Versions.
- File modifications and autosave.
- Backend startup and Workspace locking.
- Frontend navigation and settings.
- Existing tests.

Identify reusable components and any necessary changes.

Pay particular attention to whether file contents are duplicated in conversation history and whether the backend can continue a Run while the browser is disconnected.

Prepare a concise implementation plan, then implement it.

Do not stop after planning.

# PART A — AGENT RUNTIME

## 3. Single-Agent Execution

Implement a reliable Agent loop that can:

- Understand a user's task.
- Plan the required operations.
- Select relevant Skills and Tools.
- Execute multiple steps.
- Inspect Tool results.
- Decide what to do next.
- Request user authorization when required.
- Produce a final response and associated files.

Use native structured Tool Calling when supported by the configured model.

Validate Tool names and arguments before execution.

Do not interpret arbitrary LLM text as executable Tool requests.

Keep execution bounded with reasonable limits on model calls, Tool calls, retries, time, and resources.

The Agent should stop, ask for approval, or report a limitation rather than continue indefinitely.

### Persistent execution

Integrate Agent execution with the existing Run Manager.

Record LLM calls, Tool calls, selected Skills, execution results, errors, approvals, and generated Artifacts.

The frontend must show Agent activity as it happens.

Closing the browser must not terminate the Run.

The user must be able to reconnect and inspect the same Run without triggering duplicate execution.

Approval requests must remain available after browser disconnection and backend restart.

Avoid repeating side-effecting operations during recovery.

---

# PART B — CAPABILITY RESOLUTION POLICY

## 4. How the Agent Chooses Its Capabilities

The Agent must follow this order when determining how to complete an operation.

### Priority 1 — Reuse Existing Capabilities

First determine whether the task can be completed by:

- An existing Tool.
- An existing Skill.
- A sequence of existing Tools.
- A combination of existing Skills and Tools.

Prefer composing available capabilities where practical.

### Priority 2 — Upgrade Existing Capabilities

If the existing capabilities are insufficient, determine whether upgrading an existing Tool or Skill would make the task possible.

For example, an existing Tool might need a new parameter, an additional supported operation, or improved handling of a particular input.

Prefer an appropriate upgrade over creating a redundant capability.

### Priority 3 — Create Reusable Capabilities

If reuse and upgrading are unsuitable, consider creating a new Skill or Tool, or a small set of complementary Skills and Tools.

**Newly created Skills and Tools must be reusable.**

They must serve a reasonably defined class of tasks, with useful input parameters, documented behaviour, and appropriate error handling.

Do not create a permanent capability solely to execute one isolated operation.

### Priority 4 — `py_run_code`

If the required operation is one-time, highly specific, or too specialized to justify a reusable capability, consider the restricted `py_run_code` Skill.

It is the last resort.

The Agent must explain why existing capabilities, upgrades, and new reusable capabilities are unsuitable.

### Decision records

When the Agent proposes an upgrade, creation, or last-resort execution, record the alternatives it evaluated and why it selected that approach.

Avoid unnecessary lengthy analysis when an existing Tool clearly solves the task.

This priority is an execution-planning policy, not an authorization mechanism. Every operation remains subject to its security requirements.

# PART C — SKILLS AND TOOLS

## 5. Tool Registry

Implement a Tool Registry that lets the Agent discover and execute available operations.

Each Tool should have a clear purpose, input contract, version, permissions, security classification, and execution implementation.

Start with practical file operations such as:

- List directories.
- Search filenames and file contents.
- Read files and selected ranges.
- Inspect file metadata.
- Read historical Artifact Versions.
- Write files.
- Compare files.

Reuse existing file management code where possible.

Do not expose unrestricted filesystem or shell access through ordinary Tools.

All Tool execution must pass through backend validation and authorization.

## 6. Skill Registry

Implement reusable Skills using a straightforward format, preferably compatible with `SKILL.md` and supporting files.

Skills should be discoverable by their purpose.

Load relevant Skill instructions when needed rather than including every Skill in every LLM request.

A Skill may use multiple Tools.

A Skill cannot override a Tool's execution permissions.

Skill files and instructions must not be treated as a source of administrative authority.

Any executable scripts associated with Skills must use an authorized execution mechanism.

---

# PART D — FILES, FOLDERS AND ARTIFACTS

## 7. Dialogue Workspace and External Folders

Each Dialogue already has its own Workspace. Preserve it as the default working directory.

The Agent must also be able to access external folders that the user explicitly authorizes.

Users must be able to manage these folders entirely through the HTML frontend.

Provide:

- Add Folder.
- Remove Folder.
- View Folder.
- Change Permission.
- Show accessibility and permission status.

Support two directory permissions:

- **Read Only**
- **Read & Write**

Default external folders to Read Only.

Folder permissions should be associated with the relevant Dialogue. Do not automatically grant every Dialogue access to all external folders.

Adding, removing, or changing a folder must not require restarting the backend or manually editing configuration files.

The backend must enforce permissions on every operation.

A folder's Read & Write authorization does not automatically remove Tool-level confirmation requirements.

### Nested directories

An Agent may create or modify files directly in subdirectories of an authorized writable external folder.

For example, if a parent directory is authorized, the Agent may choose an appropriate nested location for generated files.

Do not require all generated files to be placed in the Dialogue Workspace.

Prevent path traversal and access outside authorized boundaries, including through Windows junctions, symbolic links, and other indirect paths.

Revoking folder access must prevent subsequent unauthorized operations.

## 8. Versioning External Files

Extend the existing Artifact Version system to include files created or modified directly in writable external folders.

The current file should remain in its actual external location.

Historical versions and associated metadata should be managed by the application's Artifact Store.

A versioned external file should retain its folder identity, relative path, relevant Run, content hashes, and version history.

### Expected behaviour

When an Agent modifies an existing external file:

- Preserve the original contents as a recoverable version where necessary.
- Record the new version.
- Associate the change with the relevant Run.
- Detect conflicting changes made by other programs.
- Avoid silently overwriting unexpected modifications.

Users must be able to inspect, compare, and restore file versions through the existing Files interface.

Restoring an external version should update the actual external working file, subject to current permissions and conflict checks.

Do not require the user to move the file back into the Dialogue Workspace.

Handle interruptions between external file updates and Artifact metadata updates with a recoverable process.

Do not claim full transaction isolation against unrelated external applications that do not follow the application's locking protocol.

If a user edits a tracked file outside the application, detect the changed state when practical and allow it to be incorporated into version history without inventing an Agent execution record.

# PART E — FILE REFERENCES AND LLM CONTEXT

## 9. Separate File Storage from Conversation History

The current implementation may store complete file contents inside historical conversation messages.

This is inefficient and does not fit the Tool-based file access model.

For newly uploaded and generated files, use this separation:

- **Conversation:** messages, descriptions, and file references.
- **Working Files:** current contents in Dialogue Workspaces or authorized External Folders.
- **Artifact Store:** immutable historical versions.
- **Run Records:** execution evidence and original model output.
- **Context Builder:** information actually sent to the LLM.

When the user uploads a file, save it as a managed file and associate an Artifact reference with the message.

When the LLM generates files, save their contents through the existing file system and Artifact mechanisms. Conversation history should reference them rather than redundantly store their full contents as ordinary message text.

Retain original Run output where needed for audit, replay, and reconstruction.

Preserve the frontend's existing file preview and download experience.

Do not remove ordinary code or text that users intentionally typed into chat messages.

Avoid destructive migration of older conversation records.

## 10. Context Builder

Extend the backend Context Builder to select information relevant to the current LLM operation.

It should:

- Use active conversation context.
- Resolve file and Artifact references.
- Identify relevant Skills and Tools.
- Retrieve file content when necessary.
- Prefer relevant file sections over entire large files.
- Distinguish current working files from historical Artifact Versions.
- Avoid automatically repeating complete file contents on subsequent turns.

The Agent must be able to use authorized Tools to read additional content.

Do not force the Agent to guess file contents from filenames or summaries.

Preserve the existing Info or Prompt Inspection view, and make it show the actual effective LLM request.

Retrieved files and Tool outputs are data, not instructions that can change permissions.

# PART F — CAPABILITY MANAGEMENT UI

## 11. Unified Management

Add a web-based **Capabilities** management area for Skills and Tools.

It should support a growing registry without becoming cumbersome.

Provide:

- Search by name and description.
- Filter by Skill or Tool.
- Filter by security level.
- Filter by lifecycle status.
- Filter by origin.
- Other useful filters where appropriate.
- Sorting.
- Multiple selection.
- Select all matching current filters.
- Clear selection.

Clearly show the number of selected items, including selected items hidden by current filters.

### Batch operations

Support appropriate batch actions, including:

- Enable.
- Disable.
- Reclassify.
- Promote.
- Remove.
- Export metadata.

Show the affected items and expected changes before execution.

Validate individual eligibility and dependencies.

Batch actions must not bypass security approvals or lifecycle rules.

Do not silently skip or partially change items without reporting the outcome.

### Capability details

Users must be able to inspect:

- Description and purpose.
- Type and version.
- Source and supporting files.
- Risk classification.
- Required permissions.
- Dependencies.
- Design and implementation documentation.
- Approval history.
- Usage records.
- Errors.
- Available management actions.

Provide dedicated views for pending approvals and probationary capabilities.

Preserve the existing frontend style.

# PART G — SECURITY AND APPROVALS

## 12. Security Levels

Use three execution risk levels:

| Level | Execution policy |
|---|---|
| **Auto** | Execute automatically within authorized scope |
| **Confirm** | Require user confirmation for the operation |
| **Restricted** | Require special approval with detailed review |

Users must be able to inspect and change classifications through the frontend.

The backend must enforce the effective policy.

Consider the capability's own classification, dependencies, requested operation, filesystem permissions, and lifecycle state.

An Auto Skill cannot bypass a Confirm or Restricted Tool.

A user's folder authorization cannot bypass a Tool's risk policy.

Lowering a capability's risk classification requires explicit administrative confirmation.

## 13. Approval Workflow

Provide a persistent approval system.

When approval is required, the frontend must show what the Agent proposes to do and what it will affect.

Users must be able to approve or reject the request.

For Restricted operations, require a detailed application.

Approvals must remain available while the browser is closed and after backend restart.

Bind execution approvals to the reviewed operation, capability version, relevant inputs, code hashes, and permissions.

A changed operation or changed executable source requires a new approval.

The Agent must never approve its own requests or change its own permission records.

Administrative actions must be protected from unauthorized requests.

# PART H — CAPABILITY CREATION AND UPGRADES

## 14. Agent-Created Skills and Tools

Provide restricted creation capabilities, such as:

- `create_skill`
- `create_tool`

These allow the Agent to propose reusable capabilities.

Running the creation workflow requires special authorization.

Separate permission to **prepare a candidate** from permission to **install and activate the candidate**.

A candidate must not become executable merely because the Agent generated its files.

### Required proposal

Every creation proposal must contain:

1. **Purpose:** what the capability does.
2. **Alternatives:** which existing Skills and Tools were examined, and why they are insufficient.
3. **Reusability:** what future tasks the capability can serve.
4. **Design:** inputs, outputs, workflow, dependencies, and failure conditions.
5. **Implementation Notes:** readable explanations of the implementation and important design choices.
6. **Complete Source:** all source code, instructions, scripts, and relevant configuration.
7. **Permissions:** requested filesystem, network, process, and other access.
8. **Tests:** relevant cases, results, and limitations.
9. **Risk Assessment:** likely failure modes and a suggested security classification.
10. **Rollback:** how the capability can be disabled or restored.

The application must be understandable to a human reviewer.

Avoid generic or promotional explanations.

The user must explicitly approve the candidate and assign or confirm its risk classification.

The approval must apply to the exact reviewed version.

## 15. Upgrading Existing Capabilities

The Agent must also be able to propose an improved version of an existing Skill or Tool.

An upgrade follows the same review, authorization, and approval requirements as creation.

Additionally, the proposal must explain:

- What is wrong or missing in the current version.
- What changes are proposed.
- How the interface or behaviour changes.
- Whether existing dependent capabilities remain compatible.
- What regression tests were performed.

Provide a readable source diff.

When approved, the new version **replaces the old version as the active implementation**.

Preserve the old version for rollback.

Do not overwrite historical version contents in place.

Both newly created capabilities and approved upgrades enter Probation.

# PART I — CAPABILITY VERSIONING AND PROBATION

## 16. Capability Versions

Skills and Tools must have versioned source Artifacts.

Users should be able to:

- Inspect version history.
- View source.
- Compare versions.
- Activate an approved version.
- Restore a previous version.
- Remove a capability from active use.
- Permanently delete a selected bad version.

Use the existing Artifact infrastructure where appropriate.

Store source versions and their approval history with sufficient integrity to verify exactly what was approved and executed.

Changing source code requires a new version and appropriate review.

### Restore

Restoring a previous version changes which implementation is active.

Check its integrity, compatibility, permissions, and current approval requirements.

Record the change.

Do not silently substitute a different implementation.

### Permanent deletion

Distinguish ordinary Remove from permanent version deletion.

**Remove** makes the capability unavailable while retaining its history.

**Purge** deletes the selected managed version's actual source package so that it cannot be activated or restored.

Purge requires explicit special confirmation.

Before Purge, explain:

- Which version is affected.
- Whether it is active or in use.
- Which capabilities depend on it.
- What historical reproducibility will be lost.
- Whether copies remain in Runs, exports, or backups.

Preserve a minimal audit record of deletion without retaining the purged source in the active version store.

Do not claim secure physical erasure unless it can actually be guaranteed.

Do not delete unrelated Run records or Memory evidence as an unintended side effect.

## 17. Probation

Every approved new capability or upgrade enters **Probation**.

Probation is independent of risk classification.

During Probation:

- Usage is recorded.
- Failures are recorded.
- Execution requires at least confirmation.
- Restricted operations remain Restricted.
- The user can inspect, disable, remove, or reclassify the capability.

Provide a dedicated Probation management view.

Allow the user to **Promote** a capability after reviewing its implementation and actual performance.

Promotion must not automatically reduce its security classification.

A promoted Restricted capability remains Restricted.

## 18. Dynamic Loading

Approved Skills and Tools must become available without restarting the Python backend.

The Registry must support changing active capability versions at runtime.

Keep source versions immutable.

Running Agent tasks should retain enough version information for reproducibility.

Revoking or disabling a capability must prevent subsequent unauthorized execution.

Do not import arbitrary Agent-generated Python code directly into the main FastAPI process.

Use an appropriate controlled execution mechanism for dynamically generated executable Tools.

A user approving a capability does not mean its code is safe to run with unrestricted backend privileges.

If reliable execution isolation is not available, keep executable dynamic capabilities disabled and report the limitation rather than implementing an unsafe shortcut.

# PART J — LAST-RESORT PYTHON EXECUTION

## 19. `py_run_code`

Provide a special Restricted Skill named:

**`py_run_code`**

This Skill allows the Agent to propose Python code for a specific, one-time operation.

It is not intended to replace the reusable Tool and Skill system.

It must follow the Capability Resolution Policy.

### Required approval application

Before execution, the Agent must explain:

- What operation is required.
- Why existing Skills and Tools cannot complete it.
- Why upgrading existing capabilities is unsuitable.
- Why creating a reusable Skill or Tool is not justified.
- What the proposed Python code will do.
- What inputs it requires.
- What files and resources it will access or modify.
- What output it should produce.
- What risks and side effects it has.

Provide the complete Python source, readable design comments, and implementation comments.

The user must inspect and approve the exact proposed code and permissions.

Approval must be invalidated if the code or execution-relevant inputs change.

### Execution safety

Never execute untrusted generated Python inside the main backend process.

Use a controlled execution environment with enforceable restrictions.

It must prevent unauthorized access to credentials, Registry files, approval records, other Dialogue Workspaces, and unapproved external folders.

Network access should be denied by default.

Apply appropriate time, resource, and process limits.

Record stdout, stderr, exit status, errors, and generated files.

A simple subprocess with a timeout is not sufficient to claim secure isolation.

If secure execution cannot be verified on the existing Windows environment, deliver the proposal and approval interface but leave actual arbitrary-code execution disabled.

Do not automatically register code executed through `py_run_code` as a reusable capability.

# PART K — CONTEXT-AWARE EXECUTION SCHEDULING

## 20. Minimize LLM Execution Cost

Large LLM contexts can cause significant prefill delays, especially with local models.

The Agent should plan its work to reduce unnecessary LLM calls and avoid unnecessarily large contexts.

Implement **Context-Aware Execution Scheduling**.

The objective is to improve total task latency and efficiency without sacrificing correctness.

### 20.1 Prefer Focused Calls

When planning a task, prefer:

- Deterministic Tool execution where sufficient.
- Reuse of previously established conclusions.
- Small, relevant LLM contexts.
- Targeted file retrieval.
- Limited repetition of previously supplied data.
- Appropriate model selection and reasoning effort.

Do not mechanically split every task into many small calls.

One sufficiently informative larger call can be better than many dependent small calls.

Use judgment based on actual total cost and expected quality.

### 20.2 Dependency-Aware Scheduling

Identify which operations depend on earlier results and which can execute independently.

Independent operations may be reordered to reduce execution cost.

For example, several analyses sharing a common source context may be executed together, even if the original task description listed them in another order.

This is similar to scheduling film production by shared locations and resources instead of filming strictly in story order.

Preserve necessary dependencies and user priorities.

Do not reorder side-effecting actions in ways that change their intended behaviour.

### 20.3 KV-Cache Awareness

Consider KV-cache locality when scheduling LLM requests.

Where practical, arrange compatible independent calls near one another when they share an identical reusable token prefix.

Consider:

- Model identity.
- Endpoint and inference configuration.
- Stable system instructions.
- Selected Tool and Skill definitions.
- Shared context.
- Prompt-prefix identity.
- Cache residency.

**Semantically similar prompts do not necessarily share KV cache.**

A high cache-hit percentage does not necessarily imply low prefill latency.

Do not assume cache reuse across different model instances or incompatible prompts.

Keep common prompt prefixes stable where practical, but never preserve stale permissions or context merely to improve cache reuse.

Do not implement a separate KV-cache system. Use the facilities of the configured LLM server.

Inspect the actual caching capabilities of the installed model server.

### 20.4 Scheduling Priorities

Balance:

1. Correct task dependencies.
2. User responsiveness.
3. Total task latency.
4. Number and size of LLM calls.
5. Uncached prefill cost.
6. KV-cache reuse.
7. Background maintenance work.

Do not delay interactive work indefinitely for caching opportunities.

Keep the scheduling implementation proportionate to the existing application.

### 20.5 Performance Measurements

Record useful metrics where available:

- Number of LLM calls.
- Input and output tokens.
- Cached and uncached input tokens.
- Prefill duration or time to first token.
- Total call duration.
- Total Run duration.
- Relevant context or prefix identity.

Distinguish measured values from estimates.

Provide a practical way to compare ordinary dependency-order execution against the optimized scheduler.

Do not claim success based on cache-hit rate alone.

# PART L — AGENT MEMORY

## 21. Memory Design

Introduce a persistent Agent Memory system.

The purpose is to preserve useful conclusions from completed work while reducing the amount of historical context needed for future LLM calls.

**Agent Memory is different from Conversation Compaction.**

The existing chat history remains the user's conversation record.

Agent Memory is a compact knowledge layer derived from completed tasks and historical LLM execution records.

Original Run records must remain available.

Do not delete original historical records as a consequence of memory summarization.

Provide two built-in Skills:

- `memory_summary`
- `memory_recall`

## 22. `memory_summary`

Use the configured **Thinker LLM** to summarize completed historical Agent and LLM Runs.

Prefer records whose outcomes are already known.

The summary should preserve:

- Established conclusions.
- Verified findings.
- Important decisions.
- Useful implementation knowledge.
- Successful approaches.
- Negative findings.
- Reasons approaches failed.
- Relevant assumptions and limitations.
- Unresolved questions that matter.
- References to supporting historical records.

**Prioritize conclusions over the process used to reach them.**

Compress repetitive searches, intermediate reasoning, unsuccessful attempts, and redundant Tool output once their outcomes are understood.

However, do not erase distinctions that materially affect the conclusion.

### Memory quality

Do not turn an LLM hypothesis into a verified fact simply because it appears in a summary.

Distinguish verified findings, inferences, disputed claims, and unresolved questions.

Preserve relevant conditions, such as the applicable source version.

If later evidence contradicts an earlier conclusion, retain the provenance and mark the earlier conclusion appropriately rather than silently replacing history.

### Summarization strategy

Avoid feeding an enormous Run Archive into one Thinker request unnecessarily.

Use incremental or hierarchical summarization where useful.

Store concise summaries with references to the original Run, steps, Tool results, and Artifact Versions.

Memory summaries should themselves be versioned.

Summarization should be available on demand and may also run automatically after eligible work completes.

Background summarization must have lower priority than interactive user tasks.

Avoid recursively summarizing the summarization process itself.

### Memory scope

Use appropriate Dialogue and Workspace boundaries.

Do not automatically expose one Dialogue's records to another Dialogue without authorization.

Do not allow Memory to bypass file permissions or other security restrictions.

## 23. `memory_recall`

Provide a Skill that lets the Agent retrieve the original evidence behind a Memory summary.

The Skill should support searching historical conclusions and following references to their original records.

The Agent may use it when:

- A summary lacks necessary details.
- The user asks why a conclusion was reached.
- The Agent needs to verify the original evidence.
- The original implementation process matters.
- Later evidence conflicts with an earlier conclusion.

Prefer progressive retrieval:

1. Find relevant summaries.
2. Identify their source references.
3. Retrieve relevant Run steps.
4. Retrieve original Tool results or file versions when needed.
5. Return the precise historical evidence.

Do not automatically load an entire historical Run into the LLM context when only a few details are required.

Original Run records must remain intact and retrievable.

If a record is unavailable, report that limitation. Do not fabricate the missing process.

Recall must enforce current access permissions.

## 24. Memory and Context Builder Integration

The Context Builder should use relevant Agent Memory before reopening large historical records.

For a new task, provide concise established conclusions where useful.

Use `memory_recall` only when the underlying details are needed.

Do not inject every Memory summary into every LLM call.

Coordinate Memory updates with the Context-Aware Scheduler.

A shorter context is generally useful, but changes to prompt prefixes can reduce cache reuse. Optimize based on actual task performance rather than a fixed assumption.

### Frontend Memory Management

Provide a lightweight Agent Memory interface.

Users should be able to:

- Browse and search summaries.
- Inspect conclusions and their status.
- See supporting references.
- Open originating Runs.
- Trigger summarization.
- Recall historical details.
- Identify superseded findings.

Reuse the existing Runs and Files views for detailed evidence.

Avoid building an unnecessary separate knowledge-management application.

# PART M — PERSISTENCE, RELIABILITY AND SAFETY

## 25. Storage and Recovery

Reuse the current filesystem-based persistence system.

Keep records for:

- Agent execution.
- Skills and Tools.
- Capability versions.
- Security classifications.
- Approval decisions.
- Probation and promotion.
- Folder permissions.
- External file versions.
- Memory summaries and provenance.

Use stable identities, integrity checks, and atomic or recoverable updates where appropriate.

Keep sensitive Registry administration files outside ordinary Agent-writable locations.

Agent file Tools must not modify approval records, security policies, or capability source packages directly.

Preserve existing single-instance and Workspace locking behaviour.

Avoid introducing additional services unless necessary.

## 26. Failure Handling

Handle failures explicitly.

An Agent Run may fail, be cancelled, be interrupted, or wait for approval.

A Tool may fail without corrupting the broader application.

A newly approved capability may fail without crashing the Python backend.

A file update may conflict with external edits.

A capability upgrade may need rollback.

Memory summarization may fail without affecting the original Run.

The system should preserve useful partial results and accurate execution records.

Do not silently mark unsuccessful operations as completed.

# PART N — TESTING AND ACCEPTANCE

## 27. Testing Approach

Use the existing test framework.

Use deterministic mock LLM behaviour for repeatable Agent, streaming, approval, and recovery tests.

Also test against configured real LLM endpoints where practical.

Test actual backend authorization, not only frontend controls.

### Required end-to-end scenarios

**A. Multi-step Agent Task**

Ask the Agent to inspect the application's Python source, trace a feature across files, and produce a report.

Verify that it selects and chains existing Tools, records its steps, and saves the result.

**B. External Folder Management**

Add an External Folder through the frontend.

Test Read Only and Read & Write access, nested file creation, permission changes, and revocation.

**C. External File Versioning**

Modify an existing file directly in an external subfolder.

Verify original-version capture, new-version publication, comparison, rollback, and conflict detection.

**D. Capability Creation**

Have the Agent identify a missing reusable capability.

Verify that it examines existing alternatives, prepares a complete proposal, receives approval, and installs the new version under Probation.

**E. Capability Upgrade**

Upgrade an existing Tool or Skill.

Verify source diffs, compatibility tests, approval, new active version, Probation, and restoration of an earlier version.

**F. Capability Purge**

Permanently delete a test capability version.

Verify that it is no longer executable or restorable from managed capability storage, while appropriate audit history remains.

**G. Capability Management**

Test filtering, sorting, multiple selection, batch operations, reclassification, promotion, disable, and removal.

Verify that batch operations do not bypass security requirements.

**H. Restricted Python**

Have the Agent propose a one-off Python operation.

Verify the four-level Capability Resolution assessment, complete source review, special approval, and controlled execution if verified safe.

If isolation cannot be verified, demonstrate that execution remains disabled.

**I. Context-Aware Scheduling**

Give the Agent several tasks with shared and independent contexts.

Compare normal execution against context-aware scheduling.

Measure total latency and available token/cache statistics.

Verify correct dependency handling.

**J. Memory Summary and Recall**

Complete a multi-step investigation.

Use Thinker to produce a conclusion-oriented Memory summary.

Start a related task and verify that the Agent uses the summary.

Then ask why the conclusion was reached and verify that `memory_recall` retrieves the correct original Run details.

Confirm that the original records remain intact.

**K. Persistent Approval**

Start an Agent task requiring user approval.

Close the browser and reopen the application.

Approve the pending request and verify that the original Run continues without duplicate execution.

Also verify correct recovery after backend restart.

**L. Regression**

Confirm that the existing Chatbox, model selection, reasoning display, streaming, Undo/Redo, Runs, autosave, Workspaces, file versions, and prompt inspection continue to work.

## 28. Definition of Done

Phase 3 is complete when:

- The Agent can execute bounded multi-step tasks.
- Skills and Tools are registered, discoverable, and usable.
- The four-level Capability Resolution Policy is implemented.
- Users can manage External Folders through the frontend.
- External file writes are associated with Artifact Versions.
- Users can manage and batch-select Skills and Tools.
- Risk classifications and approvals are enforced by the backend.
- The Agent can propose reusable Skills and Tools.
- The Agent can propose upgrades to existing capabilities.
- New and upgraded versions require review and approval.
