## Persistent Runs, Dialogue Workspaces, File Versioning, and Autosave

### 1. Objective

Extend the completed Phase 1 Chatbox into a persistent task and file workspace.

Phase 1 is already implemented and working. Use its existing codebase as the starting point.

Phase 2 must add five capabilities:

1. **Workspace Setup:** Configure and change the Workspace Root from the frontend.
2. **Persistent Runs:** Continue LLM generation after the browser disconnects. Reconnect to the original Run without repeating it.
3. **Dialogue Workspaces:** Give each Dialogue its own persistent directory containing real files.
4. **Files Workspace:** Preview, download, compare, and restore generated file versions.
5. **Autosave:** Automatically preserve unsent input, dialogue settings, streaming output, and file drafts.

The backend must operate as a **single-instance application**, with operating-system-level locks protecting the backend instance and active Workspace.

Use the existing Python backend and local filesystem.

Start Phase 2 with a new, empty Workspace. No Phase 1 conversation history, files, or other records need to be migrated.

**The deliverable must be a working application with all Phase 1 features preserved.**

Do not implement Agent orchestration, Skills, Java integration, or Alpha Research functionality in Phase 2.

---

## 2. Development Principles

Follow these rules:

1. Inspect the actual Phase 1 implementation before making changes.
2. Preserve existing functionality and frontend behaviour.
3. Reuse existing code, APIs, and storage conventions where practical.
4. Keep the code simple and readable.
5. Avoid unnecessary frameworks, abstractions, and dependencies.
6. Do not introduce microservices or distributed execution.
7. Use native Windows execution.
8. Use human-readable files for persistent records.
9. Do not simulate LLM output, file generation, or task progress.
10. Do not remove working features to simplify implementation.
11. Use clear, concise English in the interface. Prefer ASD-STE100-style wording.
12. Keep authoritative application state in Python.
13. Use deterministic code for state transitions, versioning, and recovery.
14. Investigate source code and logs before requesting information from the user.
15. Do not expand the scope into future phases.

Do not stop after producing an implementation plan.

Proceed with implementation, testing, and delivery.

# PART A — SINGLE BACKEND INSTANCE

## 4. Single-Instance Runtime

Silico must operate as a single-backend-instance application.

Only one backend instance may run for the same application installation and supported Windows user environment.

Multiple browser clients may connect to that backend.

Multiple Dialogues may exist.

Multiple LLM Runs may be managed by the backend, subject to configured concurrency limits.

Do not implement coordination between independent backend processes.

Use one FastAPI application worker.

Do not configure multiple Uvicorn workers.

Do not use an automatic-reload configuration that creates competing application instances.

### 4.1 Backend Instance Identity

Generate a stable Instance ID during initial setup.

Store it outside the Workspace Root.

Suggested location:

```text
%LOCALAPPDATA%\Silico\
    instance-config.json
    backend.lock
```

Example:

```json
{
  "schema_version": 1,
  "instance_id": "stable-generated-instance-id",
  "workspace_root": "D:\\Silico\\Workspace"
}
```

Use existing configuration conventions when practical.

The Bootstrap Configuration must not depend on the Workspace Root being available.

### 4.2 Instance Lock

Acquire an exclusive operating-system-level lock during backend startup.

Hold the lock for the entire backend process lifetime.

If another backend already holds the lock:

- Do not load or modify application state.
- Do not start another Run Manager.
- Report a clear error.
- Exit safely.

Use a Windows-compatible OS file-locking mechanism, such as `portalocker`.

Do not rely only on file existence, PID records, or timestamps.

The operating system must release the lock when the owning process terminates unexpectedly.

A stale lock file without an active OS lock must not prevent startup.

### 4.3 Lock Lifecycle

Acquire the instance lock before opening persistent application state.

Release it during normal shutdown.

Keep the lock handle alive for the required lifetime.

Use FastAPI lifespan management or a similarly clear lifecycle mechanism.

Avoid locking during module import if that would make testing or development tools unreliable.

# PART B — WORKSPACE ROOT

## 5. Workspace Root Configuration

Silico must use one active Workspace Root at a time.

The user must be able to configure and change this Root through the frontend.

The Workspace Root is a directory on the computer running the Python backend.

Users must not need to select a directory for each Dialogue.

### 5.1 Initial Setup

On frontend startup, query the backend Workspace configuration.

Suggested endpoint:

`GET /api/workspace/config`

Example response:

```json
{
  "configured": false,
  "instance_id": "instance-id",
  "workspace_root": null
}
```

If no valid Root is configured:

1. Display a Workspace Setup screen.
2. Explain what the Workspace stores.
3. Ask the user to enter the Workspace Root path.
4. Offer to create the directory if it does not exist.
5. Send the configuration to Python.
6. Validate and initialize the Workspace.
7. Open the normal Chatbox after setup succeeds.

Keep health and Workspace Setup APIs available before initialization.

Do not enable persistent Dialogue or Run operations until a valid Workspace is active.

Do not silently select a temporary Workspace.

If the previously configured Root is unavailable, show an error instead of automatically creating a replacement.

### 5.2 Frontend Setup UI

Use the existing frontend design.

Suggested wording:

**Set up your workspace**

"Select a folder on the computer that runs the Silico backend. Silico will store conversations, generated files, and task records in this folder."

Provide:

- Workspace Root path input.
- Path validation feedback.
- Create Workspace action.
- Open Existing Workspace action.

A browser's normal folder picker selects a directory on the browser's computer, which may not be the backend computer.

Do not assume the browser and backend run on the same machine.

A path input field is sufficient for Phase 2.

Do not build an elaborate server-side filesystem browser.

### 5.3 Root Validation

Validate:

- Absolute path.
- Directory existence.
- Write permissions.
- Existing Workspace metadata.
- Workspace schema compatibility.
- Lock availability.
- Invalid or unsafe filesystem locations.

Do not overwrite unrelated files.

If a compatible Workspace already exists, open it.

If an empty directory is selected, allow explicit initialization.

If a directory contains unrelated files, do not automatically treat it as an empty Workspace.

### 5.4 Workspace Identity

Each Workspace Root must have a stable Workspace ID.

Store it in `workspace.json`.

Example:

```json
{
  "schema_version": 1,
  "workspace_id": "stable-workspace-id",
  "created_at": "2026-11-22T12:00:00Z"
}
```

The Workspace ID and Backend Instance ID are different identifiers.

Do not regenerate a Workspace ID when reopening it.

---

## 6. Workspace Lock

Every Workspace Root must have an OS-level lock file.

Suggested name:

`.workspace.lock`

Acquire an exclusive operating-system-level lock before normal Workspace operations.

Hold the lock while the Workspace is active.

If the lock cannot be acquired:

- Do not modify Workspace data.
- Report that the Workspace is in use.
- Allow the user to select another directory.

Do not rely on the lock file's existence.

Do not automatically delete a lock file because its stored PID appears inactive.

Do not force-unlock a Workspace held by another live process.

Support local filesystem locking.

Do not claim arbitrary network filesystem compatibility without verification.

### 6.1 Purpose of the Two Locks

The Instance Lock prevents two Silico backend processes from running for the same installation.

The Workspace Lock prevents another process from concurrently writing into the active Workspace.

Keep both mechanisms.

Do not introduce a distributed lock service.

---

## 7. Workspace Settings and Switching

Add a **Workspace Settings** view to the frontend.

This is separate from the model connection configuration removed in Phase 1.

Do not reintroduce the Model Config tab.

Display:

- Backend Instance ID.
- Workspace ID.
- Current Workspace Root.
- Workspace accessibility and write status.
- Number of queued and active Runs.
- Change Workspace action.

Support:

1. Create a new Workspace.
2. Open an existing compatible Workspace.

Do not automatically copy or migrate data from one Workspace to another.

### 7.1 Safe Switching

A Workspace switch must:

1. Prevent new Run creation and conflicting state mutations during the transition.
2. Check that no Runs are queued or active.
3. Reject the operation if queued or active Runs exist.
4. Validate the target directory.
5. Acquire the target Workspace Lock.
6. Validate target metadata and storage.
7. Prepare the target Workspace.
8. Atomically update the Bootstrap Configuration.
9. Activate the target Workspace.
10. Release the previous Workspace Lock.
11. Refresh frontend state.

If switching fails, preserve the previous Workspace.

Do not release the previous Workspace Lock before the replacement is ready.

Handle failures and process termination during switching.

On restart, open the Root specified by the durable Bootstrap Configuration.

### 7.2 Stale Browser Requests

A browser may still display the previous Workspace after another browser switches Roots.

Use Workspace identity and revision checks where needed.

Reject stale state-changing requests.

Do not allow a delayed request to modify an unintended Workspace.

### 7.3 Administrative Access

Changing Workspace Root is an administrative operation.

Default to a backend bound to the local machine.

If remote browser access is supported, protect Workspace configuration APIs with appropriate authentication and authorization.

Do not permit arbitrary unauthenticated remote users to select server filesystem paths.

# PART C — DIALOGUE WORKSPACES

## 8. One Workspace per Dialogue

Each Dialogue must have its own persistent subdirectory.

Create it automatically.

Use the stable Dialogue ID as the directory identifier.

Do not use the Dialogue title as a directory name.

A Dialogue Workspace belongs to the Dialogue, not to a browser session.

Closing or refreshing the browser must not create another Workspace.

Reopening a Dialogue must restore its original Workspace.

### 8.1 Recommended Directory Layout

```text
WorkspaceRoot/
│
├── workspace.json
├── .workspace.lock
│
├── dialogues/
│   ├── dlg_001/
│   │   ├── dialogue.json
│   │   ├── workspace.json
│   │   ├── input_draft.json
│   │   └── workspace/
│   │       ├── alpha.py
│   │       └── analysis.md
│   │
│   └── dlg_002/
│       ├── dialogue.json
│       ├── workspace.json
│       ├── input_draft.json
│       └── workspace/
│
├── runs/
│   ├── run_001/
│   │   ├── run.json
│   │   ├── request.json
│   │   ├── events.jsonl
│   │   └── drafts/
│   └── run_002/
│
└── artifacts/
    └── artifact_001/
        ├── manifest.json
        └── versions/
            ├── v001/
            └── v002/
```

This layout is a suggestion.

Adapt it to existing code conventions.

No Phase 1 historical data needs to be migrated into it.

### 8.2 Real Working Files

Each Dialogue's `workspace/` directory must contain actual files.

These files must be accessible using Windows Explorer and ordinary text editors.

They are the current working copies, not immutable historical versions.

Published historical versions are stored in the shared Artifact Store.

Do not use symbolic links as the default implementation.

### 8.3 Workspace Manifest

Maintain a manifest for the logical files in each Dialogue.

Example:

```json
{
  "dialogue_id": "dlg_001",
  "revision": 4,
  "files": {
    "alpha.py": {
      "artifact_id": "artifact_001",
      "current_version_id": "v002",
      "content_sha256": "..."
    }
  }
}
```

The manifest records the current published version associated with each working file.

If a file was modified outside the application, detect that its content differs from the recorded hash.

Do not silently overwrite externally modified files.

### 8.4 Workspace Isolation

Different Dialogues may contain identical filenames.

One Dialogue must not modify another Dialogue's Workspace implicitly.

All Dialogues may share the backend Artifact Store for immutable versions.

Do not implement automatic cross-Dialogue file sharing in Phase 2.

### 8.5 Dialogue Deletion

Do not silently destroy historical Runs or Artifact Versions when a Dialogue is removed.

Use a simple recoverable deletion or archive policy where appropriate.

Document the behaviour.

Do not implement complex retention management.

# PART D — PERSISTENT RUNS

## 9. Run Manager

A Run represents one execution of an LLM generation request.

Each Run must have a unique stable identifier.

The Run Manager must execute in Python.

A Run must not depend on an open browser connection.

### 9.1 Run States

Support:

| State | Meaning |
|---|---|
| `queued` | Accepted and waiting |
| `running` | Executing |
| `completed` | Finished successfully |
| `failed` | Execution failed |
| `cancelled` | Explicit cancellation completed |
| `interrupted` | Execution stopped unexpectedly |

Do not treat browser disconnection as cancellation.

Do not assume the HTTP stream closing means successful model completion.

Record the provider finish reason separately.

### 9.2 Run Creation

When the user sends a message:

1. Validate the Dialogue and its current revision.
2. Capture the effective conversation context.
3. Capture the selected model and generation parameters.
4. Capture the active Workspace identity.
5. Create a persistent Run record.
6. Save the effective request without credentials.
7. Queue the Run.
8. Return its Run ID.
9. Execute it independently of the browser connection.

Use an idempotency key.

If an identical request is retried with the same key, return the original Run ID.

Reject reuse of a key with a different payload.

Do not execute duplicate LLM requests because of network retries.

### 9.3 Run Record

Store at least:

```json
{
  "run_id": "run_001",
  "workspace_id": "workspace-id",
  "dialogue_id": "dlg_001",
  "run_type": "llm_generation",
  "status": "running",
  "created_at": "2026-11-22T12:00:00Z",
  "started_at": "2026-11-22T12:00:01Z",
  "completed_at": null,
  "model_profile_id": "coder",
  "dialogue_revision": 12,
  "last_event_seq": 35,
  "retry_of": null
}
```

Keep the request snapshot immutable.

Changing Dialogue settings must not modify a running request.

### 9.4 Execution

Use a small application-managed Run Manager.

It must:

- Start queued requests.
- Track active requests.
- Enforce concurrency limits.
- Handle explicit cancellation.
- Persist streaming events.
- Save generated file drafts.
- Finalize Run outcomes.
- Release resources.

A single asynchronous worker is sufficient initially.

Do not introduce Redis, RQ, Celery, or a database.

Do not create unmanaged threads for each HTTP request.

---

## 10. Browser Disconnect and Reconnection

### 10.1 Browser Disconnect

Closing the browser or disconnecting the streaming connection must not cancel the Run.

The backend must continue:

- Upstream LLM generation.
- Event persistence.
- Draft file persistence.
- Run-state management.

Only an explicit Stop action should request cancellation.

### 10.2 Reconnection

When the user reconnects:

1. Retrieve the original Run status.
2. Retrieve persisted events.
3. Restore previously generated content.
4. Continue receiving new events if the Run is active.

Do not start another LLM request.

Do not regenerate the previous output.

### 10.3 Event Replay

Persist streaming events in JSONL.

Example:

```json
{
  "schema_version": 1,
  "run_id": "run_001",
  "seq": 36,
  "timestamp": "2026-11-22T12:00:05Z",
  "type": "message.delta",
  "payload": {
    "text": "Generated text..."
  }
}
```

Use monotonically increasing sequence numbers per Run.

Provide an endpoint to retrieve events after a specified sequence.

Example:

`GET /api/runs/{run_id}/events?after_seq=35`

Support historical replay followed by live events.

Avoid gaps between replay and live streaming.

The frontend must suppress duplicate sequence numbers.

### 10.4 Persist Before Broadcast

Persist events before broadcasting them.

Small bounded batches are acceptable.

Do not require a disk write for each token.

Only committed events may be described as durably saved.

The event log must be sufficient to reconstruct streamed output after reconnecting.

### 10.5 Cancellation

Explicit Stop must:

1. Identify the active Run.
2. Request cancellation.
3. Cancel or close the upstream LLM request where supported.
4. Preserve received output.
5. Preserve draft files.
6. Record the correct terminal state.
7. Allow another request.

Handle cancellation/completion races.

---

## 11. Backend Restart and Recovery

An unexpected backend termination may stop active LLM generation.

Do not attempt exact-token resumption in Phase 2.

### 11.1 Startup Reconciliation

On startup:

1. Acquire the Instance Lock.
2. Read the Bootstrap Configuration.
3. Acquire the Workspace Lock.
4. Load the Workspace.
5. Inspect persisted Run records.
6. Identify abandoned active Runs.
7. Mark them `interrupted`.
8. Preserve their events and drafts.
9. Begin accepting new requests.

Do not leave abandoned Runs indefinitely marked `running`.

Do not automatically restart interrupted Runs.

### 11.2 Retry

Allow retry of failed or interrupted Runs.

A retry must:

- Create a new Run ID.
- Reference the original Run.
- Preserve the original request snapshot unless the user explicitly changes it.
- Preserve the original events and artifacts.
- Avoid duplicating conversation messages.

If active Dialogue history has changed, do not silently overwrite it.

Do not describe restarting generation as continuing from the interrupted token.

# PART E — FILES AND VERSIONING

## 12. File Lifecycle

Generated files have three distinct forms:

**Run Draft**

Incomplete or in-progress generated content.

**Published Artifact Version**

A structurally complete, immutable file version.

**Dialogue Working File**

The current editable file in a Dialogue Workspace.

Do not combine these into one mutable record.

### 12.1 Drafts

During generation:

- Save drafts under the generating Run.
- Update drafts incrementally.
- Make them available for preview.
- Mark them as incomplete until completion is validated.
- Preserve them after cancellation or interruption.

Inspect and reuse the existing file-generation format.

Do not assume the model always follows the expected file format.

Retain the original model output.

If file boundaries are ambiguous, preserve the content as a draft instead of automatically publishing it.

### 12.2 Publication

When file generation finishes:

1. Validate its logical path.
2. Validate file boundaries.
3. Confirm the relevant Run outcome permits publication.
4. Save immutable content.
5. Calculate its SHA-256 hash.
6. Write version metadata.
7. Finalize publication.
8. Update the Dialogue Working File when safe.

Do not overwrite existing versions.

Structural completion does not imply executable-code correctness.

Do not introduce code compilation in Phase 2.

### 12.3 Artifact Identity

Use stable Artifact and Version IDs.

Store:

- Artifact ID.
- Version ID.
- Dialogue ID.
- Logical filename.
- Generating Run ID.
- Parent Version ID.
- Creation time.
- Content hash.
- File size.
- Publication status.

### 12.4 Current Working Files

After publication, update the real working file when safe.

Before replacing an existing file, verify:

- Workspace revision.
- Current version pointer.
- Current file content hash.

If the user or another process changed the file after the Run started, preserve both contents.

Do not silently overwrite the user's changes.

Save the generated content as another version and report the conflict.

### 12.5 Compare Versions

Provide a working version comparison view.

Users must be able to choose two versions and inspect their differences.

A line-based unified diff is sufficient for text files.

Use readable formatting.

### 12.6 Restore Versions

Restoration must:

1. Load a selected historical version.
2. Create a new immutable version with the restored content.
3. Record the source version.
4. Update the current working file.
5. Update the Workspace manifest.
6. Preserve all previous versions.

Restoration is an explicit user action.

It must not change the conversation history.

### 12.7 Download

Allow users to download generated files.

Preserve logical filenames.

Validate paths.

Display potentially executable content safely.

Do not execute generated HTML or JavaScript in a privileged application context.

# PART F — AUTOSAVE

## 14. Autosave

Implement autosave for all relevant working state.

The backend must remain authoritative.

### 14.1 Conversation Changes

Persist accepted conversation changes immediately.

This includes:

- Sent messages.
- Completed response commits.
- Undo.
- Redo.
- Regeneration.
- Dialogue rename.
- Dialogue deletion or archival.

Preserve Phase 1 semantics.

### 14.2 Dialogue Settings

Autosave:

- Model selection.
- Temperature.
- Max Tokens.
- Top P.
- Top K.
- Min P.
- Repetition Penalty.
- Presence Penalty.
- Reasoning Effort.
- Other existing Dialogue settings.

Use a short debounce for rapid changes.

Validate changes in Python.

Do not show a failed save as successful.

### 14.3 Unsent Input

Autosave the unsent message draft for each Dialogue.

Use approximately 500–800 ms debounce.

Flush pending changes when switching Dialogues where possible.

Restore the draft when reopening the Dialogue.

If the backend is unavailable, retain unsaved input in the frontend and indicate that it has not been saved.

Do not rely only on browser unload events.

### 14.4 Streaming Output

Persist streaming events continuously in bounded batches.

Commit events before broadcasting them.

Do not rewrite large conversation records per token.

### 14.5 Generated File Drafts

Save drafts incrementally during generation.

Keep incomplete drafts after interruption.

Do not publish incomplete files automatically.

### 14.6 Browser File Editing

If the current frontend supports editing files, preserve it.

Autosave working-file changes using a short debounce.

Do not create an immutable version for each keystroke.

Use revisions or content hashes to detect conflicts.

### 14.7 Save Feedback

Use concise status text where necessary:

- Saving
- Saved
- Not saved
- Save failed

Only show Saved after backend confirmation.

# PART H — STATE OWNERSHIP

## 16. Conversation, Run, and Artifact State

Keep these separate.

**Conversation** determines the active LLM context.

**Run** records a particular execution and its outputs.

**Artifact** records a logical file and its versions.

One Conversation can have many Runs.

One Run can produce multiple Artifact Versions.

### 16.1 Undo and Redo

Undo/Redo changes the active conversation context.

It must not delete Runs.

It must not delete Artifact Versions.

It must not automatically restore an old working file.

File restoration is independent.

### 16.2 Completion and Reconnection

Reconnecting must not duplicate assistant messages.

Use stable message and Run identifiers.

If the active Dialogue revision changed during a Run, preserve the Run result but do not overwrite newer conversation state.

### 16.3 Multiple Browser Windows

Allow multiple browser windows to connect to the same backend.

Use revisions to reject stale modifications.

Do not implement a collaborative text editor.

# PART I — FILESYSTEM SAFETY

## 17. Filesystem Integrity

Use JSON, JSONL, and ordinary files.

Do not introduce a database.

### 17.1 Atomic Writes

Use atomic replacement for mutable JSON records.

Write temporary files on the same filesystem.

Publish new content only after successful writing and validation.

For multi-file operations, define a clear commit point and recovery behaviour.

### 17.2 Event Logs

Use append-only JSONL.

Detect incomplete trailing entries.

Preserve event ordering and unique sequence numbers.

### 17.3 Artifact Versions

Published versions must be immutable.

Use content hashes for integrity checks.

Do not update a Workspace manifest before its referenced Artifact Version is ready.

### 17.4 Path Safety

Prevent:

- Directory traversal.
- Absolute logical artifact paths.
- Unsafe symbolic-link and reparse-point traversal.
- Access outside the configured Workspace.
- Arbitrary filesystem paths supplied by LLM output.

The backend resolves all paths.

### 17.5 Resource Limits

Provide configurable limits for:

- Generated file size.
- Files per Run.
- Total output per Run.
- Active Runs.

Do not automatically delete historical Runs or Artifact Versions.

Document backup and disk usage.

# PART K — TESTING

## 19. Automated Tests

Implement tests using existing project conventions.

Use a deterministic local mock LLM for streaming, cancellation, and interruption tests.

### 19.1 Instance Locking

Verify:

- The first backend acquires the Instance Lock.
- A second backend cannot acquire it concurrently.
