# Phase 1 Development Instruction
## Migrate the Existing Chatbox to a Python Backend

### 1. Objective

Migrate the existing HTML/JavaScript Chatbox to a Python backend.

The Python backend must become the single source of truth for:

- LLM model connection configuration.
- LLM request construction and execution.
- Conversation and dialogue history.
- Per-dialogue model selection and generation parameters.
- System prompts.
- Undo, Redo, and regeneration state.
- LLM streaming and cancellation.
- Prompt inspection.
- Persistent application records.

The frontend must send user actions to the backend and render the resulting state.

**Use local files and directories for persistent storage. Do not use a database.**

The deliverable must be the existing Chatbox running with the new Python backend, while preserving all existing working functionality.

This is Phase 1 of a longer project that will eventually develop into an Agentic Alpha Research System.

Do not implement future Agent or Alpha Research functionality in this phase.

---

### 2. Development Principles

Follow these rules:

1. Study the existing application before modifying it.
2. Preserve the existing frontend appearance and behaviour.
3. Reuse existing code wherever practical.
4. Make the smallest changes that meet the requirements.
5. Use clear, straightforward Python and JavaScript.
6. Avoid unnecessary abstraction and framework complexity.
7. Do not rewrite the frontend.
8. Do not introduce Docker, WSL, or a database.
9. Do not introduce additional services unless necessary.
10. Keep the application functional after the migration.
11. Use clear English in user-facing text. Prefer short, direct ASD-STE100-style sentences.
12. Do not introduce promotional text, unnecessary animations, or diagnostic displays.
13. Investigate the code, logs, and configuration before asking the user questions.
14. Do not remove an existing feature to simplify implementation.

Use the existing project conventions when they satisfy these requirements.

The final code must be understandable and maintainable by another developer without extensive framework-specific knowledge.

### 3. Development Environment

The target environment is Windows.

The user previously reported Python version `3.1.3`. Verify the actual installed version by executing:

```powershell

```

If the installed version is Python 3.13.x, use it.

If it is literally Python 3.1.3, report the compatibility problem and the required Python upgrade. Do not silently assume the version is 3.13.

Preferred technology:

| Python API | FastAPI |
| LLM communication | Async OpenAI-compatible client |
| Validation | Pydantic where useful |

Do not require:

- Docker
- WSL

- Redis
- Celery
- A distributed task queue
- A JavaScript frontend build system

Do not replace existing libraries unless required.

## 6. Model Configuration

### 6.1 Remove the Entire Frontend Model Config Section

The current frontend contains a collapsible section labelled:

`MODEL CONFIG`

It allows the user to configure:

- Model label.
- Base URL.
- API key.
- Model ID.
- Supported reasoning effort levels.
- Configuration reset.

**Remove this entire section from the frontend.**

Remove its related UI controls, event handlers, and browser-side credential persistence.

Do not replace it with another model configuration page.

Model endpoint configuration must be maintained exclusively in the Python backend.

### 6.2 Backend Model Configuration

Support multiple named model profiles.

At minimum, retain:

- `thinker`
- `coder`

The backend must support different OpenAI-compatible endpoints for these profiles.

Use a backend-only configuration file.

Suggested example:

```yaml
models:
  thinker:
    label: "Thinker"
    base_url: "http://127.0.0.1:8001/v1"
    api_key_env: "THINKER_API_KEY"
    model_id: "thinker"
    reasoning_efforts:
      - none
      - minimal
      - low
      - medium
      - high
      - xhigh
      - max
      - auto

  coder:
    label: "Coder"
    base_url: "http://127.0.0.1:8002/v1"
    api_key_env: "CODER_API_KEY"
    model_id: "coder"
    reasoning_efforts:
      - low
      - high
      - max
      - auto
```

The values above are examples only.

Inspect and preserve the actual model configuration and capabilities.

Do not assume both models support all reasoning values.

API keys must be read from backend-only environment variables or protected configuration.

Do not commit real credentials to Git.

Do not expose the model connection configuration in frontend HTML or JavaScript.

### 6.3 Model Capability Metadata

Provide a read-only API for safe model metadata.

Suggested endpoint:

`GET /api/model-profiles`

Example response:

```json
{
  "models": [
    {
      "id": "thinker",
      "label": "Thinker",
      "reasoning_efforts": [
        "low",
        "high",
        "max"
      ],
      "default_reasoning_effort": "high"
    },
    {
      "id": "coder",
      "label": "Coder",
      "reasoning_efforts": [
        "low",
        "high",
        "max",
        "auto"
      ],
      "default_reasoning_effort": "auto"
    }
  ]
}
```

Also expose safe parameter defaults and supported ranges when required by the existing frontend.

Do not expose:

- API keys.
- Authentication headers.
- Backend credentials.
- Private configuration file paths.

Do not expose raw provider Base URLs unless an existing frontend function genuinely requires them and doing so is safe.

### 6.4 LLM Provider Compatibility

Inspect how the current frontend sends requests to the configured models.

Preserve the existing request formats and provider-specific behaviour.

In particular, investigate:

- Reasoning effort parameters.
- Reasoning content fields.
- Maximum completion token parameters.
- Temperature.
- Top P.
- Top K.
- Min P.
- Repetition penalty.
- Presence penalty.
- Streaming response formats.

Some OpenAI-compatible servers support additional or non-standard fields.

Preserve the behaviour that works with the current models.

Do not silently remove unsupported or non-standard parameters.

If an invalid combination is selected, use a clear validation error.

Do not assume all endpoints expose the same capabilities.

## 7. Per-Dialogue Model Selection and Parameters

**This section is a critical requirement.**

The frontend currently allows each dialogue to select its own model and generation parameters.

Preserve these controls and their behaviour.

### 7.1 Model Selection

Keep the existing Thinker/Coder selector.

Each dialogue must retain its selected model.

For example:

```text
Dialogue A
    Model: Thinker

Dialogue B
    Model: Coder

Dialogue C
    Model: Thinker
```

Switching dialogue must restore the correct selection.

Changing the selected model in one dialogue must not change other dialogues.

The backend must save the model selection.

### 7.2 Generation Parameters

Preserve every existing per-dialogue generation setting.

The currently known settings include:

| Setting | Requirement |
|---|---|
| Temperature | Preserve |
| Max Tokens | Preserve |
| Top P | Preserve |
| Top K | Preserve |
| Min P | Preserve |
| Repetition Penalty | Preserve |
| Presence Penalty | Preserve |
| Reasoning Effort | Preserve |

Inspect the current source code for any additional parameters and preserve them.

Do not change existing parameter ranges, defaults, or display conventions without a technical reason.

Preserve numeric precision and zero values.

Do not silently clamp parameters or substitute defaults.

### 7.3 Reasoning Effort

Keep the existing reasoning effort slider and related controls.

The current application supports model-specific reasoning levels.

Preserve the actual supported values and their ordering.

When the selected model changes, the frontend must display the available reasoning options for that model.

The authoritative list comes from backend model metadata.

Preserve existing behaviour when the user changes reasoning effort.

### 7.4 Backend Persistence

Store the selected model and parameters for each dialogue in the backend filesystem.

Example:

```json
{
  "dialogue_id": "dlg_001",
  "model_profile_id": "coder",
  "generation_settings": {
    "temperature": 0,
    "max_tokens": 200000,
    "top_p": 0.95,
    "top_k": 20,
    "min_p": 0,
    "repetition_penalty": 1,
    "presence_penalty": 0,
    "reasoning_effort": "auto"
  }
}
```

These values are illustrative.

Use the existing values and behaviour as the reference.

When the user changes a setting:

1. The frontend sends the change to Python.
2. Python validates the setting.
3. Python saves the setting.
4. Python returns the authoritative value.
5. The frontend updates its display.

A failed save must not appear successful.

Settings must survive application restarts.

### 7.5 Settings During Generation

When a request starts, create an immutable snapshot of the effective model settings.

Changes made after the request starts must not silently alter the running request.

The updated settings apply to subsequent requests.

The Info window must show the settings actually used for that request.

## 8. Conversation History Management

Move conversation history management entirely to Python.

The backend must manage:

- Dialogue creation.
- Dialogue deletion.
- Dialogue renaming.
- Message storage.
- Active conversation history.
- System prompts.
- Dialogue settings.
- Undo.
- Redo.
- Regeneration.
- Conversation revisions.

The frontend only sends actions and renders backend state.

### 8.1 Backend as Single Source of Truth

The backend determines which messages are active.

The frontend must not submit the entire conversation history with every new message.

Instead, it submits the dialogue identifier and current user action.

For example:

```json
{
  "dialogue_id": "dlg_001",
  "content": "Explain this function"
}
```

The backend loads the relevant state and constructs the effective LLM context.

### 8.2 Undo and Redo

Preserve the exact Undo/Redo behaviour of the current application.

At minimum:

1. Support multiple consecutive Undo operations.
2. Support multiple consecutive Redo operations.
3. Undo must not immediately destroy message history.
4. A user must be able to restore an undone turn before a new response is committed.
5. A successful new response may close the old Redo branch.
6. A failed or cancelled response must not accidentally destroy the recoverable Redo branch.
7. Regeneration must preserve the current application's branching semantics.

Inspect what the existing application considers one Undo unit.

If it treats one user question and its assistant answer as a single turn, preserve that behaviour.

Do not change the unit of Undo.

### 8.3 Pending Generation

Distinguish between:

- Committed conversation turns.
- A user message awaiting a response.
- A response currently streaming.
- A completed response.
- A cancelled or failed run.

Do not treat partial streaming content as a fully completed assistant response.

Preserve already displayed content when a generation is cancelled or fails.

Keep enough information to inspect or retry a failed generation.

Do not incorrectly advance the committed history or destroy the previous Redo branch.

Use the existing user-facing behaviour as the compatibility reference.

### 8.4 Autosave

Preserve autosave.

The backend must persist authoritative conversation state.

Conversation history and settings must survive:

- Browser refresh.
- Frontend restart.
- Backend restart.

The frontend should not require a manual Save action.

### 8.5 Concurrent Actions

Use a revision number or equivalent mechanism.

Prevent stale frontend actions from overwriting newer dialogue state.

Use stable action identifiers to avoid duplicate operations caused by HTTP retries.

For Phase 1, allow only one active generation per dialogue unless the existing application already defines different behaviour.

Keep concurrency handling straightforward.

### 9.2 Dialogue Storage

Use a human-readable JSON record for each dialogue.

Store:

- Dialogue ID.
- Title.
- Created and updated timestamps.
- Selected model profile.
- Generation settings.
- System prompt.
- Committed messages.
- Active-history state.
- Undo/Redo state.
- Revision information.

A single atomic dialogue snapshot is acceptable for Phase 1.

It avoids unnecessary coordination between multiple files during a history update.

Do not rewrite the dialogue snapshot for every streamed token.

Store streaming records separately and commit conversation state at appropriate transition points.

### 9.3 Run Storage

Store each LLM generation in a separate run directory.

Suggested files:

**request.json**

The effective LLM request used for the run, excluding credentials.

**events.jsonl**

Structured generation and execution events.

**status.json**

Run identity, dialogue ID, model, timestamps, final status, finish reason, token usage when available, and errors.

Make these records readable using ordinary text editors.

Use descriptive field names and ISO 8601 timestamps.

### 9.4 File Integrity

Implement:

- Atomic replacement of mutable JSON files.
- Serialized writes or per-dialogue locks.
- Safe appending to JSONL.
- Detection of incomplete trailing JSONL entries.
- Recovery from interrupted writes.
- Stable unique identifiers.
- Validation of file paths.
- Protection against directory traversal.

Avoid complicated transaction frameworks.

For multi-file updates, clearly define which file is authoritative and how interrupted operations are reconciled.

Use the smallest reliable solution.

### 9.5 Administrative Inspection

An administrator must be able to inspect:

- Dialogue history.
- Model selection.
- Generation parameters.
- Active and undone turns.
- LLM requests.
- Run status.
- Errors.
- Streaming events.

No database software or custom administration interface should be necessary.

Document the directory structure and record formats.

Do not use pickle or opaque binary serialization.

### 9.6 Storage Boundary

Keep filesystem operations inside a small storage module.

Expose simple operations such as:

```python
load_dialogue(dialogue_id)
save_dialogue(dialogue)
list_dialogues()
create_dialogue(settings)
load_run(run_id)
save_run_status(run_id, status)
append_run_event(run_id, event)
```

These are conceptual operations. Adapt them to the actual implementation.

Do not build a generic database abstraction framework.

The purpose is to keep file-format details out of the API and LLM code.

## 11. LLM Request Construction

The Python backend must construct the complete request.

For each generation:

1. Load the active dialogue.
2. Load its current model selection.
3. Load the backend model configuration.
4. Load the saved generation parameters.
5. Load the active conversation history.
6. Load the current system prompt.
7. Construct the provider request.
8. Record the safe effective request.
9. Start streaming.

Preserve current system prompt semantics and message ordering.

Do not inject additional system messages unless required by existing behaviour.

Do not add Skills or Tool Definitions in Phase 1.

If an existing application feature already uses command-related messages, preserve its established behaviour. Do not introduce new command execution or expand existing permissions.

The backend must validate dialogue state before starting a request.

## 12. Streaming Protocol

Use an HTTP streaming response.

Prefer newline-delimited JSON (NDJSON).

Each event must include:

```json
{
  "schema_version": 1,
  "run_id": "run_001",
  "seq": 1,
  "type": "message.delta",
  "payload": {
    "text": "Hello"
  }
}
```

Use a unique `run_id` for each generation.

Sequence numbers must increase monotonically within the run.

### Required Event Types

| Event | Purpose |
|---|---|
| `run.started` | Generation started |
| `request.prepared` | Safe request inspection data is available |
| `message.delta` | Incremental assistant text |
| `reasoning.delta` | Provider-supplied reasoning |
| `run.completed` | Generation completed |
| `run.cancelled` | Generation cancelled |
| `run.failed` | Generation failed |

Define a consistent payload for each event.

The frontend must display text as soon as it arrives.

Do not wait for the complete response.

Handle:

- Provider chunks containing partial JSON.
- UTF-8 characters split across reads.
- Multiple logical events in one network chunk.
- Unexpected provider disconnects.
- Empty streams.
- Cancellation while streaming.
- Provider completion metadata.

Do not confuse transport completion with successful generation.

Preserve the existing code and file rendering behaviour.

Do not introduce a new artifact-management subsystem.

### 12.1 Reasoning

Some models provide separate reasoning output.

Forward it when the endpoint actually provides it.

Keep reasoning separate from normal assistant text.

Preserve the existing reasoning panel, formatting, and scrolling.

Do not fabricate reasoning output.

Do not assume every model provides the same reasoning fields.

## 13. Cancellation

Preserve the existing Stop button.

A Stop action must:

1. Identify the active generation.
2. Request cancellation from Python.
3. Cancel or close the upstream LLM request where supported.
4. Stop further response display.
5. Preserve already received content.
6. Save accurate run status.
7. Leave the dialogue in a consistent state.
8. Permit the next request to start.

Handle cancellation and normal completion occurring at nearly the same time.

Do not report a completed run as cancelled.

Do not allow abandoned requests to continue consuming model resources unnecessarily.

An in-memory active-run registry is acceptable for Phase 1.

Use a single backend worker if the implementation depends on process-local cancellation state.

A browser disconnect must have clearly defined cancellation behaviour.

Do not implement general long-running task recovery in this phase.
